## Запуск

Нужен только Docker: .NET SDK и Node.js устанавливать не требуется — всё
собирается внутри контейнеров.

```bash
# 1. Склонировать репозиторий
git clone https://github.com/waleron07/timesheet-test-task.git
cd timesheet-test-task

# 2. Поднять всё одной командой (первый запуск — несколько минут на сборку)
docker compose up --build -d

# 3. Наполнить базу приёмочными данными из задания
docker compose exec api dotnet Timesheet.Api.dll seed

# 4. Открыть интерфейс
open http://localhost:5173

# 5. Прогнать приёмочные проверки (необязательно, но быстрее, чем руками)
./scripts/acceptance.sh
```

| Сервис | Адрес |
|---|---|
| Интерфейс | http://localhost:5173 |
| API | http://localhost:8080 |
| Swagger | http://localhost:8080/swagger |
| Healthcheck | http://localhost:8080/api/health |
| MongoDB | localhost:27017, база `timesheet` |

Остановить: `docker compose down` (с `-v` — вместе с данными MongoDB).

## Тестовые данные

Команда `seed` **идемпотентна и сносящая**: очищает коллекции и заливает ровно
приёмочный набор из задания — 2 сотрудника, 2 проекта, 4 записи табеля.

Это важно при проверке. Сценарии с ошибками создают в базе лишние записи —
в частности, 20 часов Иванову на 06.03.2026 сохраняются успешно, так и
задумано, — после чего отчёт за март показывает 32 часа вместо ожидаемых 12
по П-001. Порядок работы:

```
seed → сверить отчёты → прогнать сценарии с ошибками → seed заново
```

`./scripts/acceptance.sh` делает это сам: сносит данные до и после прогона.

## Проверка

### Приёмочные проверки из задания

```bash
./scripts/acceptance.sh
```

Скрипт прогоняет по живому API обе таблицы отчётов и все восемь сценариев с
ошибками — **36 проверок**, включая коды ошибок, а не только HTTP-статусы:

```
Отчёт за март 2026:     П-001 — 12 ч, 7 600 ₽, 38 %
                        П-002 — 10 ч, 7 000 ₽, 140 %, перерасход
                        Итого — 22 ч, 14 600 ₽
Отчёт за февраль 2026:  П-001 — 8 ч, 4 000 ₽, 20 %
```

| Сценарий | Ответ |
|---|---|
| Петрова 15.01.2026 — нет ставки | `400 RATE_NOT_FOUND` |
| Иванов 06.03, 20 ч | `201`, день помечен переработкой |
| Ещё 6 ч тем же днём — 26 ч | `409 DAILY_LIMIT_EXCEEDED` |
| П-002 датой 20.02 | `400 DATE_OUT_OF_PROJECT_RANGE` |
| Правка в закрытом феврале | `409 PERIOD_CLOSED` |
| Часы 0 или 3,7 | `400 VALIDATION_FAILED` |
| Сохранение из двух вкладок | `409 CONCURRENT_MODIFICATION` |
| Ставка 600 → 650 задним числом | запись 05.03 → 5 200 ₽, П-001 → 8 000 ₽ |

Плюс шесть проверок границ, которые ТЗ не оговаривает явно: создание и удаление
в закрытом периоде, перенос записи в закрытый период и из него, ровно 24 часа
одной записью, запись в последний день проекта.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/time-entries` | список за месяц: `year`, `month`, `employeeId`, `projectId`, `page`, `pageSize` |
| `PUT` | `/api/time-entries` | создать запись |
| `POST` | `/api/time-entries/{id}` | изменить запись |
| `DELETE` | `/api/time-entries/{id}` | удалить запись |
| `GET` | `/api/reports/projects` | отчёт по проектам: `year`, `month` |
| `GET` | `/api/employees`, `/api/projects` | справочники |
| `GET` | `/api/periods` | закрытые периоды |
| `POST` | `/api/periods/close`, `/api/periods/open` | закрыть и открыть месяц |

Создание через `PUT`, а изменение через `POST /{id}` — обратно привычной
семантике HTTP, но так задано в ТЗ и реализовано без самовольных изменений
(см. [`NOTES.md`](NOTES.md), п. 1.6).

Ошибки бизнес-правил приходят как `400`, `409` или `404` с телом
`{ "code": "PERIOD_CLOSED", "message": "Период 02.2026 закрыт бухгалтерией…" }`.
Коды: `INVALID_HOURS`, `RATE_NOT_FOUND`, `DATE_OUT_OF_PROJECT_RANGE`,
`DAILY_LIMIT_EXCEEDED`, `PERIOD_CLOSED`, `CONCURRENT_MODIFICATION`,
`VALIDATION_FAILED`.

## Структура

```
├── src/
│   ├── Timesheet.Domain/          сущности и бизнес-правила
│   │                              без зависимостей на MongoDB и ASP.NET
│   └── Timesheet.Api/
│       ├── Contracts/             DTO API — отдельно от модели БД
│       ├── Features/              команды и запросы (MediatR)
│       ├── Infrastructure/        доступ к MongoDB, индексы, пайплайны, сид
│       ├── Middleware/            превращение исключений в коды ошибок
│       └── Controllers/           тонкие контроллеры
├── tests/Timesheet.Tests/         юнит-тесты бизнес-правил
├── web/                           React 18 + TypeScript + Vite
├── scripts/acceptance.sh          прогон приёмочных проверок
├── code-review/                   часть 1: исходники и исправленные версии
└── docker-compose.yml
```

Два принципа, которые выдержаны по всему коду:

1. **Домен не знает ни про MongoDB, ни про HTTP.** Бизнес-правила проверяются
   без поднятой базы, маппинг задаётся `BsonClassMap` в инфраструктуре,
   сопоставление ошибок с HTTP-статусами — в middleware.
2. **Отчёт и список считаются в базе.** Ни одного места, где записи табеля
   выгружаются в память для подсчёта: агрегация, `$facet`-пагинация,
   выбор ставки на дату прямо в пайплайне.

Подробности и обоснования — в [`NOTES.md`](NOTES.md).
