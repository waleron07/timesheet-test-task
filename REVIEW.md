## TimesheetReportHandler.cs

### 1. Вся коллекция `time_entries` загружается в память (критично)

```csharp
var entries = await _db.GetCollection<TimeEntry>("time_entries")
    .Find(FilterDefinition<TimeEntry>.Empty)
    .ToListAsync();

var monthEntries = entries
    .Where(e => e.Date.Year == request.Year && e.Date.Month == request.Month)
```

Фильтр по месяцу выполняется в LINQ-to-Objects **после** выгрузки всей коллекции.
Mongo отдаёт все записи за всю историю, чтобы C# оставил из них один месяц.

**Чем грозит.** На «нескольких миллионах» записей это десятки-сотни мегабайт на
каждый вызов отчёта: рост LOH, GC pauses, OOM при паре параллельных запросов.
Отчёт — операция, которую в конце месяца жмут все разом. Плюс сеть и время
сериализации BSON. На тестовой базе в тысячу записей это незаметно — именно
поэтому дефект дожил до прода.

**Как чинить.** Считать отчёт **агрегацией на стороне Mongo**: `$match` по
диапазону дат → `$lookup` ставок → `$group` по проекту → `$lookup` проектов.
В C# приходит уже готовый набор строк отчёта — по одной на проект.
Важно: фильтровать не `$year`/`$month` от поля (это убивает индекс), а
полуинтервалом `date >= 2026-03-01 && date < 2026-04-01` — такой предикат
использует индекс по `date`.

### 2. Ставка выбирается неверно — берётся произвольная, а не действовавшая на дату (критично, деньги)

```csharp
var rate = employee.Rates.FirstOrDefault().Value;
```

По домену `Rates` — это история пар «ставка, действует с даты», и стоимость
записи должна считаться по ставке, действовавшей **на дату записи**. Здесь
берётся первый элемент массива в том порядке, в каком он лежит в документе.

**Чем грозит.** Молча неверные деньги во всех отчётах. Ошибка не падает,
не логируется и не видна на глаз — цифры «выглядят правдоподобно». Если ставку
добавили задним числом (а по ТЗ так можно) или порядок в массиве изменился,
суммы поедут задним числом по всей истории. Это худший класс багов: расхождение
находит бухгалтерия через квартал.

**Как чинить.** Выбирать ставку с максимальным `From <= entry.Date`. В агрегации —
`$filter` по `from <= date` и `$reduce` для взятия максимальной `from`
(портируемее, чем `$sortArray`, которому нужен Mongo 5.2+).

### 3. `.Result` внутри async-метода (критично)

```csharp
var employee = _db.GetCollection<Employee>("employees")
    .Find(e => e.Id == entry.EmployeeId)
    .FirstOrDefaultAsync().Result;
```

Синхронное блокирующее ожидание асинхронной операции.

**Чем грозит.** В ASP.NET Core (без legacy SynchronizationContext) дедлока не
будет, но поток пула блокируется на время каждого сетевого запроса. В цикле по
записям это thread pool starvation: при нагрузке пул не успевает добавлять
потоки (~1 поток/сек), очередь запросов растёт, растёт latency всего сервиса,
а не только отчёта. Плюс исключение приедет завёрнутым в `AggregateException`.

**Как чинить.** `await`. А после исправления №1 этот вызов вообще исчезает.

### 4. N+1 запросов к базе (критично)

Внутри `foreach` по записям — запрос в `employees` на **каждую** запись
(без кеша, один и тот же сотрудник запрашивается сотни раз) и запрос в
`projects` на каждый новый проект.

**Чем грозит.** На 100 000 записей за месяц — 100 000 round-trip'ов к Mongo.
Даже по 1 мс это 100 секунд: отчёт уходит в таймаут HTTP-клиента, соединения
из пула Mongo заняты, страдают соседние эндпоинты.

**Как чинить.** Тем же: агрегация с `$lookup`. Если бы соединения оставались
в C# — грузить сотрудников и проекты одним `Find(In(x => x.Id, ids))` и класть
в словарь.

### 5. `CancellationToken token` принимается и никуда не передаётся (высокая)

Ни один из трёх вызовов к Mongo не получает `token`.

**Чем грозит.** Пользователь закрыл вкладку / клиент отвалился по таймауту —
сервер продолжает молотить тяжёлый отчёт до конца. При таймауте на фронте люди
жмут «обновить», и каждый повтор добавляет ещё одну неубиваемую задачу.
Классический путь к каскадной деградации.

**Как чинить.** Прокидывать `token` во все асинхронные вызовы драйвера
(`AggregateAsync(..., token)`, `cursor.ToListAsync(token)`).

### 6. `NullReferenceException` в трёх местах (высокая)

```csharp
var rate = employee.Rates.FirstOrDefault().Value;   // employee == null; Rates == null; Rates пуст
...
ProjectId = project.Id,                              // project == null
```

- `employee` не найден (запись ссылается на удалённого сотрудника) → NRE;
- `Rates == null` или пустой → NRE (а по ТЗ «нет ставки на дату» — это штатная,
  ожидаемая ситуация, а не сбой);
- `project` не найден → NRE.

**Чем грозит.** Одна битая ссылка в данных — и весь отчёт отдаёт 500 без
объяснения. Пользователь не может построить отчёт вообще, и по 500 непонятно,
какая именно запись виновата. В Mongo нет FK, поэтому висячие ссылки — не
гипотетический случай, а вопрос времени.

**Как чинить.** Отчёт не должен падать из-за одной записи: `$lookup` с
`preserveNullAndEmptyArrays`, отсутствующее имя проекта → `«Проект не найден»`,
записи без применимой ставки — не молча в 0, а отдельным счётчиком
`EntriesWithoutRate` в строке отчёта, чтобы расхождение было **видно**.
Тихое приведение к нулю здесь хуже падения.

### 7. Деньги в `double` (высокая)

`Amount`, `Budget`, `Rate.Value`, `Percent` — `double`.

**Чем грозит.** `double` — двоичная плавающая точка, 0.1 в ней непредставима.
При суммировании тысяч строк ошибка накапливается, и отчёт расходится с
бухгалтерией на копейки-рубли; `Math.Round(x, 2)` этого не лечит, потому что
округляется уже испорченное значение, а следом снова идёт сложение. Плюс
`Math.Round` по умолчанию банковское (к чётному): 2.345 → 2.34, что расходится
с ожиданием бухгалтера.

**Как чинить.** `decimal` в C#, `Decimal128` в Mongo (`[BsonRepresentation]` или
хранение как `NumberDecimal`), округление явным `MidpointRounding.AwayFromZero`.
`Hours` можно оставить дробным, но кратность 0,5 — тоже кандидат на `decimal`.

### 8. Деление на ноль в проценте освоения (средняя)

```csharp
row.Percent = Math.Round(row.Amount / row.Budget * 100, 2);
```

При `Budget == 0` в `double` получается `Infinity` (или `NaN` при `0/0`) —
исключения не будет.

**Чем грозит.** `Infinity`/`NaN` — невалидный JSON по RFC 8259.
`System.Text.Json` на такое кидает исключение при сериализации → 500 уже после
того, как отчёт посчитан. Если сериализатор настроен лояльно — на фронт уезжает
`Infinity`, и падает уже фронт. Бюджет 0 у только что заведённого проекта —
обычное дело.

**Как чинить.** `Budget > 0 ? ... : (decimal?)null` и явное отображение
«бюджет не задан» на фронте. В `decimal` деление на ноль, в отличие от `double`,
бросает `DivideByZeroException` — так что после перехода на `decimal` (п. 7)
эта проверка становится обязательной.

### 9. Округление на каждой записи, а не на итоге (средняя)

```csharp
var amount = Math.Round(entry.Hours * rate, 2);
...
rows[entry.ProjectId].Amount += amount;
```

Округление копится: 10 000 записей × до полкопейки — до 50 рублей расхождения
с суммой, посчитанной иначе.

**Чем грозит.** Отчёт по проектам не сходится с отчётом по сотрудникам за тот
же период — обе цифры «правильные», объяснить разницу невозможно.

**Как чинить.** Зафиксировать правило и держать его одним на всю систему.
Я выбрал округление **на уровне записи** (стоимость записи — это то, что
пользователь видит в табеле, и итог обязан быть суммой видимых строк), но это
осознанное решение, а не единственно верное — записал в NOTES.md.

### 10. Отсутствует валидация входных `Year` / `Month` (средняя)

`Month = 0`, `13`, `Year = 0` пройдут насквозь и дадут пустой отчёт вместо
внятной ошибки; при построении диапазона дат из таких значений
`new DateTime(year, month, 1)` бросит `ArgumentOutOfRangeException` → 500.

**Как чинить.** FluentValidation на запрос (`Month` в 1..12, `Year` в разумном
диапазоне) — по стеку он уже в проекте. Валидация формата отделена от
бизнес-правил, как и требует ТЗ.

### 11. `DateTime` без указания Kind (средняя, легко проглядеть)

`TimeEntry.Date` — `DateTime`, драйвер по умолчанию хранит в UTC и возвращает
`DateTimeKind.Utc`. Границы месяца, построенные локально, съедут на смещение
таймзоны, и записи 1-го или последнего числа месяца попадут не в тот отчёт.

**Как чинить.** Дата табеля — это календарная дата без времени: хранить как
UTC-полночь с `[BsonDateTimeOptions(Kind = DateTimeKind.Utc)]` (или `DateOnly`
с кастомным сериализатором) и строить границы месяца в UTC.

### 12. Имена коллекций строковыми литералами (низкая)

`"time_entries"`, `"employees"`, `"projects"` разбросаны по коду. Опечатка не
даёт ошибки — Mongo просто создаёт/читает пустую коллекцию, и отчёт молча
пустой. Вынести в константы или в типизированный `IMongoCollection<T>` из DI.

### 13. Сущности лежат в одном файле с хендлером (низкая)

`TimeEntry`, `Employee`, `Rate`, `Project` объявлены в
`namespace Demo.Api.Queries.Reports`. Документы БД живут в неймспейсе одного
конкретного отчёта — второй потребитель либо продублирует их, либо потянет
за собой зависимость на отчёты.

### 14. Модель БД возвращается как модель API (низкая)

`ProjectReportRow` одновременно и результат хендлера, и то, что уйдёт в JSON.
Любое переименование поля — ломающее изменение контракта.

### 15. Косметика

- `using System.Collections.Generic` и `System.Linq` останутся нужны, но
  `MediatR`-хендлер стоит пометить `sealed`;
- `Percent` считается и для строк с нулевыми часами;
- нет логирования: сколько записей обработано, сколько без ставки, сколько
  занял отчёт — при разборе расхождения это первое, чего не хватит;
- `Overspent` есть, а `AtRisk` (>80 %) из ТЗ нет — в новой версии добавлен.

## TimeEntriesPage.tsx

### 1. `useEffect` без массива зависимостей — бесконечный цикл запросов (критично)

```tsx
useEffect(() => {
    load();
});
```

Эффект без второго аргумента выполняется после **каждого** рендера. `load()`
делает `setLoading`/`setEntries` → рендер → снова эффект → снова запрос.

**Чем грозит.** Компонент бомбит `/api/time-entries` со скоростью цикла рендера —
десятки запросов в секунду с каждой открытой вкладки. Это self-DDoS: на
дев-машине с одним пользователем выглядит как «просто мигает», в проде на
сотне пользователей кладёт API. Самая опасная строка во всём файле.

**Как чинить.** `useEffect(() => { load(); }, [props.year, props.month])`, сам
`load` — в `useCallback` с теми же зависимостями.

### 2. Смена месяца не перезагружает данные (критично по логике — маскируется багом №1)

`props.year` / `props.month` не входят ни в какие зависимости. Сейчас это
«работает» только потому, что эффект и так вызывается постоянно. Как только
починят №1 наивно (`[]`), экран перестанет реагировать на смену месяца —
и появится новый баг вместо старого. Чинить эти две проблемы надо вместе.

### 3. Мутация состояния вместо создания нового массива (критично)

```tsx
entries.push(body);
setEntries(entries);
```

`push` меняет тот же самый массив, `setEntries` получает **ту же ссылку**.
React сравнивает по `Object.is`, видит равенство и рендер не запускает.

**Чем грозит.** Пользователь нажал «Добавить», увидел `alert("Сохранено")`, но
строка в таблице не появилась. Классический вывод пользователя: «ваша система
теряет данные» — хотя на сервере запись есть. Ещё и запрос уже улетел, так что
повторное нажатие создаёт дубль.

**Как чинить.** Не строить состояние вручную, а перезагрузить список с сервера
после успешного сохранения (или подставить объект **из ответа** сервера).

### 4. В состояние кладётся тело запроса, а не ответ сервера → падение рендера (критично)

`body` содержит только `employeeId`, `projectId`, `date`, `hours`. В таблице же
рендерятся `entry.employeeName`, `entry.projectName`, `entry.id` и

```tsx
<td>{entry.amount.toFixed(2)}</td>
```

`amount` у `body` — `undefined`, `undefined.toFixed` → `TypeError` → без Error
Boundary весь React-поддерево размонтируется, пользователь видит белый экран.
Сейчас спасает только баг №3 (рендера не происходит) — то есть два бага взаимно
маскируют друг друга, и починка одного вскроет второй.

**Как чинить.** Источник истины — ответ сервера: стоимость и применённую ставку
считает бэкенд, фронт их только показывает. Плюс защита при рендере
(`amount ?? 0`), раз тип приходит из сети.

### 5. Ошибки сервера полностью игнорируются (критично)

```tsx
await fetch("/api/time-entries", { method: "PUT", ... });
// ответ не проверяется вообще
alert("Сохранено");
```

`fetch` не бросает на 4xx/5xx — только на сетевом сбое. `response.ok` не
проверяется ни в `save`, ни в `load`, ни в `remove`; `try/catch` нет нигде.

**Чем грозит.** Все бизнес-ошибки из ТЗ — закрытый период, лимит 24 часа, нет
ставки на дату, конфликт версий (409) — приходят с осмысленным русским текстом
и теряются. Пользователю показывают «Сохранено». Он уходит уверенным, что
запись есть; её нет. Прямое нарушение требования «ошибки валидации с сервера
видит пользователь, а не только консоль» — здесь их не видит даже консоль.

**Как чинить.** Проверять `response.ok`, разбирать тело ошибки
(`{ code, message }`), класть в состояние и показывать в интерфейсе;
`catch` на сетевые сбои; `finally` для сброса `loading`.

### 6. `setLoading(false)` не выполнится при ошибке (высокая)

```tsx
setLoading(true);
const response = await fetch(...);   // бросок здесь — и всё
const data = await response.json();  // или здесь, если пришёл HTML/пустое тело
setLoading(false);
```

**Чем грозит.** Экран навсегда залипает в «Загрузка...», единственный выход —
перезагрузка страницы. Обрыв сети или 502 от прокси — обычное дело.

**Как чинить.** `try/catch/finally`, сброс `loading` в `finally`.

### 7. Race condition: ответы могут прийти не в том порядке (высокая)

Быстрое переключение месяцев (или текущий бесконечный цикл) запускает
параллельные `load()`. Порядок ответов не гарантирован: медленный ответ за март
может прийти после быстрого за апрель и перетереть его.

**Чем грозит.** В таблице данные не того месяца, который выбран в фильтре.
Пользователь этого не замечает — заголовок-то правильный. Дальше он на этих
данных принимает решения.

**Как чинить.** `AbortController`: отменять предыдущий запрос в cleanup-функции
эффекта, игнорировать `AbortError`. Это же решает утечку «setState после
размонтирования».

### 8. Дата отправляется в локализованном формате (высокая)

```tsx
date: new Date(date).toLocaleDateString(),
```

`toLocaleDateString()` даёт строку по локали **браузера**: `05.03.2026` в RU,
`3/5/2026` в US, а при пустом/кривом вводе — `"Invalid Date"`. Это ещё и
двойное преобразование: строка → `Date` (парсится по правилам браузера) →
снова строка.

**Чем грозит.** Один и тот же ввод даёт разные данные у разных пользователей.
`3/5/2026` бэкенд разберёт как 3 мая, а не 5 марта — запись улетит в другой
месяц, отчёт разойдётся, и воспроизвести баг у себя разработчик не сможет.
На эту же грабль наступает поле ввода: `<input placeholder="Дата">` — обычный
текст без валидации.

**Как чинить.** `<input type="date">`, который даёт ISO `YYYY-MM-DD`, и отправка
ровно этой строки. Формат обмена — всегда ISO 8601, локаль — только на
отображении.

### 9. `hours` уходит на сервер строкой (высокая)

```tsx
const [hours, setHours] = useState("");   // ...
hours: hours,                             // "8" — строка
```

Плюс `<input placeholder="Часы">` — текстовое поле без ограничений. Пустая
строка, `"восемь"`, `"-3"`, `"3,7"` (запятая!) улетают на бэкенд как есть.

**Чем грозит.** В лучшем случае 400 от бэкенда (который здесь всё равно не
показывается — см. №5), в худшем — нестрогий биндинг примет строку и в базу
ляжет мусор. Требование ТЗ «часы положительные, кратные 0,5, не больше 24»
на фронте не проверяется вообще.

**Как чинить.** Парсить в число, валидировать на клиенте до отправки
(положительные, кратность 0,5, ≤ 24) и всё равно проверять на сервере —
клиентская валидация только для удобства, не для безопасности.

### 10. `total` считается через `parseFloat` по строке (средняя)

```tsx
total = total + parseFloat(filtered[i].amount);
```

Одно `undefined`/`null` в `amount` — и `parseFloat` вернёт `NaN`, который
заражает всю сумму: итог станет `"NaN"`. Плюс суммирование денег в
`double`-семантике JS даёт классическое `0.1 + 0.2 = 0.30000000000000004`,
и итог на копейку расходится с бэкендом.

**Как чинить.** Итоги по отфильтрованному списку считать на сервере (он и так
знает суммы), а на клиенте — `reduce` с `Number(x) || 0` и округлением до
копеек. Заодно `for`-цикл на каждом рендере → `useMemo`.

### 11. `==` вместо `===` при сравнении id (средняя)

```tsx
entries.filter((e) => e.employeeId == employeeId)
```

Нестрогое сравнение здесь «спасает» от того, что типы разъезжаются (число из
API против строки из `<select>`). Это не решение проблемы, а её маскировка:
при `employeeId === ""` фильтр отключается снаружи, но `0 == ""` → `false`,
а `"0" == 0` → `true` — поведение зависит от того, какие id генерирует бэкенд.

**Как чинить.** Строгие типы для DTO и `===`. И — важнее — фильтрация по
сотруднику должна уходить **на сервер** (`employeeId` в query-параметрах), иначе
она ломается вместе с пагинацией: фильтруется только текущая страница.

### 12. `any[]` вместо типов — TypeScript выключен (средняя)

`useState<any[]>([])` для `entries` и `employees`. Именно из-за `any` компилятор
молча пропустил `entry.amount.toFixed(2)` на объекте без `amount` (№4) и
`parseFloat(number)` (№10). Типы здесь не «для красоты» — они бы поймали два
критичных бага на этапе сборки.

**Как чинить.** Объявить интерфейсы DTO (`TimeEntryDto`, `EmployeeDto`) и
включить `strict`.

### 13. `key={index}` в списках (средняя)

```tsx
{filtered.map((entry, index) => (<tr key={index}>
```

При удалении/вставке в середину React переиспользует DOM-узлы не тех строк:
состояние внутри строки (фокус, раскрытый инлайн-редактор, чекбокс) съезжает на
соседнюю запись. С кнопкой «Удалить» это особенно неприятно.

**Как чинить.** `key={entry.id}`.

### 14. Нет подтверждения удаления и оптимистичной блокировки (средняя)

`remove(id)` удаляет сразу по клику, без `confirm`. По ТЗ удаление ещё и
запрещено в закрытом периоде — ответ 409 сейчас проигнорируется, строка
исчезнет с экрана до следующего `load()`, а потом вернётся. И версия записи
(`version` из ТЗ) на фронте не хранится вообще, так что требование
«конкурентное редактирование даёт понятную ошибку» невыполнимо в принципе.

### 15. `alert()` как способ сообщить результат (низкая)

Блокирует поток, не стилизуется, не показывает несколько сообщений, невозможно
протестировать. Заменить на inline-баннер/тост в состоянии компонента.

### 16. Косметика

- `load` используется в `useEffect` (строка 21) до объявления `const load`
  (строка 30) — на рантайме работает, потому что эффект выполняется после
  рендера, но это TDZ-ловушка и ошибка `react-hooks/exhaustive-deps`;
- инлайн-стили `style={{ padding: 20 }}` вместо классов;
- у таблицы нет `<thead>` — непонятно, что за колонки, и это провал доступности;
- нет пустого состояния («записей за месяц нет») — пустая таблица выглядит как
  сломанная загрузка;
- сборка URL конкатенацией вместо `URLSearchParams`;
- нет `disabled` на кнопке во время сохранения → двойной клик = дубль записи.

## Что я изменил бы в структуре, а не в строках

**1. Отчёт — это запрос к БД, а не цикл в C#.**
Главная структурная претензия к хендлеру: он написан как императивная процедура
обхода данных, поэтому проблемы 1, 3, 4 — не три отдельных дефекта, а три
следствия одного неверного решения. Если отчёт формулируется как pipeline
(`$match` → `$lookup` → `$group`), N+1 и выгрузка в память не могут возникнуть
в принципе. Правило: агрегатные показатели считает база.

**2. Слои: документ БД ≠ доменная модель ≠ DTO ответа.**
Сейчас это одно и то же, и сущности живут в неймспейсе отчёта. Нужно:
`Domain/` (сущности + бизнес-правила), `Infrastructure/Mongo/` (документы,
маппинг, индексы, имена коллекций в одном месте), `Api/Contracts/` (DTO).
Тогда переименование поля в БД не ломает контракт API, а бизнес-правила можно
покрыть юнит-тестами без Mongo — как раз то, что требует часть 2.

**3. Выбор ставки по дате — доменное правило, а не строчка в отчёте.**
`employee.Rates.FirstOrDefault().Value` — не «мелкая ошибка», а признак того,
что правила нет как сущности. Оно понадобится минимум в трёх местах: создание
записи, редактирование, отчёт. Его место — метод
`Employee.RateAt(DateTime date)` (или `RateResolver`), покрытый тестами, а
Mongo-агрегация обязана быть его точным зеркалом. Расхождение между этими двумя
реализациями — главный риск такой архитектуры, и его надо явно закрывать
интеграционным тестом «C# и pipeline дают одну цифру».

**4. Деньги — отдельный тип на всём протяжении.**
`decimal` в C#, `Decimal128` в Mongo, единое правило округления
(`MidpointRounding.AwayFromZero`, до копеек) в одном хелпере, а не
`Math.Round` в каждом месте. Ноль допущений о том, что «double хватит».

**5. Обработка ошибок — сквозная, а не по месту.**
Бизнес-исключения (`BusinessRuleException` с машиночитаемым кодом) → один
`ExceptionHandlerMiddleware` → `ProblemDetails` с `code` + русским `message` →
один клиентский `apiFetch`, который эти ошибки разбирает и отдаёт компоненту.
Сейчас на бэкенде ошибок нет вообще (только NRE → 500), а на фронте нет ни
одной проверки — так что реализовывать надо оба конца сразу, иначе половина
работы не видна пользователю.

**6. Фронт: разделить данные и представление.**
`TimeEntriesPage` сейчас делает всё: fetch, состояние формы, фильтрация,
подсчёт итогов, вёрстка. Разнести на слой доступа к API (типизированный
клиент), стор/хук данных (`useTimeEntries` или mobx-store — кэш, инвалидация,
состояние загрузки и ошибки) и презентационные компоненты. Тогда фильтрация и
итоги естественно переезжают на сервер (иначе они несовместимы с пагинацией),
а форма добавления становится отдельным компонентом с валидацией (Formik + Yup
по их стеку) и собственной обработкой серверных ошибок.

**7. Тесты, которых нет ни одного.**
Оба файла написаны так, что протестировать их нельзя: хендлер намертво завязан
на `IMongoDatabase`, компонент — на глобальный `fetch`. После разделения слоёв
(п. 2, 3, 6) бизнес-правила тестируются без инфраструктуры, а pipeline — на
Testcontainers/`mongodb-memory-server`.
