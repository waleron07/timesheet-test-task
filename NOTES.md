## 1. Вопросы, заданные заказчику, и допущения на время ожидания ответа

Спецификация намеренно оставляет несколько мест недосказанными. Я отправил
письмо с шестью вопросами и по каждому зафиксировал рабочее допущение, чтобы
не блокировать разработку. Если ответ придёт и разойдётся с допущением —
правлю код и этот раздел.

### 1.1. Стоимость записи вычисляется при чтении, а не хранится

**Вопрос.** Денормализовать ли стоимость и применённую ставку в запись табеля?

**Допущение: нет, не денормализовать.** Приёмочный сценарий 8 требует, чтобы
изменение ставки Иванова с 01.03.2026 на 650 ₽ немедленно меняло стоимость
записи от 05.03.2026 в отчёте за март. Хранимое поле такого дать не может без
фонового пересчёта всех затронутых записей. Поэтому ставка и стоимость нигде
не хранятся: и список, и отчёт вычисляют их в момент запроса.

**Цена решения.** Логика выбора ставки по дате обязана существовать в двух
экземплярах — на C# (для проверки бизнес-правил при создании и редактировании)
и внутри Mongo-агрегации (потому что отчёт по ТЗ нельзя считать в памяти).
Это главный архитектурный риск проекта: две реализации одного правила могут
разойтись. Закрываю его интеграционным тестом, который прогоняет обе на одних
данных и сравнивает результат.

### 1.2. Переработка — признак дня, а не отдельной записи

**Вопрос.** Правило про > 12 часов сформулировано на сумму за день, а колонка
«отметка переработки» стоит в строке записи. Помечать все записи дня или только
ту, что перевалила порог?

**Допущение: флаг вычисляется на день** (сотрудник + дата, по всем проектам) и
проставляется всем записям этого сотрудника за эту дату. Обоснование: понятие
«запись, которая перевалила порог» зависит от порядка ввода — если бы Иванов
внёс те же 20 часов двумя записями в обратном порядке, подсветилась бы другая
строка. Признак дня от порядка ввода не зависит.

### 1.3. Лимит 24 часа при редактировании считается без старого значения записи

**Допущение.** При изменении существующей записи её прежние часы исключаются из
суммы дня. Иначе правка «8 ч → 9 ч» в плотном дне была бы отклонена собственным
старым значением этой же записи, что выглядит как баг.

### 1.4. Перенос записи между периодами проверяет оба периода

**Допущение.** Если запись переносят датой из открытого месяца в закрытый (или
наоборот), проверяются оба: и период исходной даты, и период новой. Отказ, если
закрыт любой из них. Логика: закрытый период должен быть неизменяем и «на
вход», и «на выход» — иначе из закрытого февраля можно было бы вынести часы,
переставив дату, и закрытие перестало бы что-либо гарантировать.

### 1.5. Итоги на Экране 1 — по всей выборке, а не по странице

**Вопрос.** «Итоги по отфильтрованному списку» при реальной серверной пагинации —
это итог по всем записям под фильтром или по видимой странице?

**Допущение: по всей выборке.** Итог по странице бесполезен для пользователя и
меняется при смене `pageSize`. Считаю в том же `$facet`, что и страницу, — то
есть за тот же запрос к базе, без второго round-trip'а.

### 1.6. PUT на создание, POST /{id} на изменение — реализую как в ТЗ

В таблице API создание — `PUT /api/time-entries`, изменение —
`POST /api/time-entries/{id}`. Это обратно привычной семантике HTTP (`PUT` —
идемпотентная замена по известному URI, `POST` — создание). **Реализую ровно
как написано**, без «улучшений»: раз тестовое отражает боевую систему, скорее
всего с этими путями уже работает существующий фронт, и самовольное
переименование сломало бы совместимость. Отмечаю как осознанное решение, а не
как недосмотр.

### 1.7. Прочие допущения, о которых не спрашивал

| Допущение | Обоснование |
|---|---|
| Дата табеля — календарная дата без времени; хранится UTC-полночь | Иначе смещение таймзоны переносит записи 1-го и последнего числа в соседний месяц. Все границы месяцев считаются в UTC |
| Округление денег — на уровне записи, до копеек, `MidpointRounding.AwayFromZero` | Стоимость записи пользователь видит в табеле, поэтому итог обязан быть суммой видимых строк. Округление на итоге дало бы расхождение с суммой строк на экране. Банковское округление (`ToEven` по умолчанию в .NET) расходится с ожиданием бухгалтера: 2,345 → 2,34 |
| Часы — `decimal`, не `double` | Кратность 0,5 проверяется как `hours * 2 == floor(hours * 2)`; на `double` такая проверка зависит от точности представления |
| Часы = 24 за одну запись допустимы | ТЗ: «не больше 24», то есть включительно. Аналогично суточный лимит: 24 — можно, 24,5 — нельзя |
| Процент освоения при нулевом бюджете — `null`, а не 0 и не «бесконечность» | Процент от нулевой базы не определён. В `double` это дало бы `Infinity` и невалидный JSON, в `decimal` — `DivideByZeroException`. На фронте выводится «—» |
| Проект без даты окончания — бессрочный | Прямо из ТЗ; в проверке границ верхняя граница просто отсутствует |
| Справочники сотрудников и проектов — только чтение | ТЗ требует только `GET /api/employees` и `/api/projects` «для выпадающих списков». Заводятся сид-командой |
| Шифр проекта уникален | Прямо из ТЗ, обеспечивается уникальным индексом, а не только проверкой в коде |
| Закрытие периода не требует, чтобы в нём были записи | Закрыть можно любой месяц; повторное закрытие уже закрытого — идемпотентно, не ошибка |
| Комментарий необязателен | В ТЗ не помечен обязательным |
| Версия записи — целое, инкрементируется при каждом изменении | Хватает для оптимистичной блокировки; ETag/`If-Match` избыточен для внутренней ERP |

## 2. Решения по реализации

### 2.1. Выбор ставки по дате — доменное правило, а не деталь отчёта

Ставка, действовавшая на дату: из истории берутся все со `from <= date`,
выбирается с максимальной `from`. Нет ни одной — запись создать нельзя
(`RATE_NOT_FOUND`).

Правило живёт отдельной тестируемой единицей (`Employee.RateAt(date)`), а не
строкой внутри обработчика отчёта. Оно нужно минимум в трёх местах: создание
записи, редактирование, отчёт. Именно отсутствие такой единицы породило
дефект №2 из `REVIEW.md`, где в отчёте бралась произвольная ставка из массива.

В Mongo то же правило выражено как `$filter` по `from <= date` плюс `$reduce`
для выбора максимальной `from`. `$reduce`, а не `$sortArray`: последний требует
MongoDB 5.2+, а `$reduce` доступен с 3.4 — у заказчика .NET 5 и, вероятно, не
самый свежий кластер. Нижняя граница версии для пайплайна в целом — 4.2 из-за
`$round` и `$set`.

### 2.2. Деньги

`decimal` в C#, `Decimal128` в MongoDB, конвенция сериализации задаётся
глобально. `double`/`float` не участвуют в денежных вычислениях нигде — включая
процент освоения бюджета. Единственная точка округления — общий хелпер, а не
`Math.Round` по месту вызова.

### 2.2a. Маппинг в MongoDB без отдельного слоя документов

Домен не содержит ни одного атрибута драйвера: маппинг задаётся явными
`BsonClassMap` в `Infrastructure/MongoSetup.cs`. Отдельного набора
классов-документов при этом нет — сущности маленькие, и третий слой дал бы
больше кода, чем пользы. Граница, которая здесь действительно важна и
соблюдена, — «модель БД ≠ DTO ответа API»: контракт API описан отдельными
типами и не ломается при переименовании поля в базе.

`decimal` регистрируется глобальным сериализатором в `Decimal128`, а не
атрибутом на каждом свойстве: так ни одно денежное поле не уедет в базу
двоичной дробью из-за забытого атрибута.

**`DateOnly` пришлось сериализовать самому** (`DateOnlyAsUtcDateSerializer`):
MongoDB.Driver 2.x не поддерживает этот тип. Дата табеля кладётся как
UTC-полночь. Альтернатива — хранить строкой `"2026-03-05"` — работает, но
диапазонные запросы по месяцу тогда сравниваются лексикографически, и любое
изменение формата тихо ломает отчёты.

### 2.3. Модель ошибок

Бизнес-правила бросают `BusinessRuleException(code, message)`, middleware
превращает их в `ProblemDetails` с машиночитаемым `code` и русским `message`.
Валидация формата входных данных (FluentValidation) отделена от бизнес-правил:
первая отвечает на вопрос «запрос вообще осмыслен», вторая — «операция
допустима в текущем состоянии базы».

| Код | HTTP | Когда |
|---|---|---|
| `INVALID_HOURS` | 400 | часы ≤ 0, > 24 или не кратны 0,5 |
| `RATE_NOT_FOUND` | 400 | на дату записи у сотрудника нет ставки |
| `DATE_OUT_OF_PROJECT_RANGE` | 400 | дата вне периода проекта |
| `DAILY_LIMIT_EXCEEDED` | 409 | сумма за день превысила бы 24 часа |
| `PERIOD_CLOSED` | 409 | период закрыт бухгалтерией |
| `CONCURRENT_MODIFICATION` | 409 | запись изменена другим пользователем |

400 против 409: 400 — запрос неверен сам по себе и не станет верным без правки
данных; 409 — запрос корректен, но конфликтует с текущим состоянием системы
(лимит дня, закрытый период, чужая правка). Клиент по коду может различать: в
первом случае надо править форму, во втором — перечитать данные.

### 2.4. Конкурентное редактирование

Оптимистичная блокировка на поле `version`. Обновление выполняется как
`UpdateOne({_id, version}, {$set: ..., $inc: {version: 1}})`; `MatchedCount == 0`
означает, что версия изменилась, и возвращается 409 `CONCURRENT_MODIFICATION`.
Пессимистичных блокировок и транзакций не требуется: конфликт затрагивает один
документ, а `UpdateOne` в MongoDB атомарен на уровне документа.

### 2.5. Пагинация

`$facet` с двумя ветками: `items` (`$skip`/`$limit`) и агрегаты (`$count` плюс
суммы часов и стоимости для итоговой строки) — одна поездка в базу вместо двух.

`skip`/`limit`, а не keyset-пагинация: экран табеля листается по страницам с
произвольным переходом, и внутри одного месяца объём данных заведомо небольшой.
Для миллионов записей в одном запросе keyset был бы обязателен, и это первое,
что я поменял бы при росте нагрузки.

Фильтры по сотруднику и проекту уходят **на сервер**, а не применяются в React.
Клиентская фильтрация несовместима с серверной пагинацией: фильтровалась бы
только текущая страница (ровно этот дефект отмечен в `REVIEW.md`, п. 11 по
фронтенду).

## 3. Индексы и их обоснование

Создаются явно и идемпотентно при старте API (`EnsureIndexes`), а не полагаются
на автосоздание.

| Коллекция | Индекс | Зачем |
|---|---|---|
| `time_entries` | `{ date: 1, employeeId: 1, projectId: 1 }` | Основной. Покрывает `$match` по диапазону месяца в списке и в отчёте; префикс `date` работает на диапазонном предикате, следующие поля — на опциональных фильтрах. Порядок именно такой: поле диапазона идёт первым, потому что фильтры по сотруднику и проекту опциональны и на них нельзя опереться как на префикс |
| `time_entries` | `{ employeeId: 1, date: 1 }` | Под проверку суточного лимита 24 часа и вычисление флага переработки: выборка всех записей одного сотрудника за конкретную дату. Здесь оба предиката — равенства, поэтому порядок диктуется селективностью |
| `projects` | `{ code: 1 }`, unique | Шифр уникален по ТЗ. Уникальность обеспечивается базой, а не только проверкой в коде: без неё гонка двух параллельных вставок даёт дубль |
| `closed_periods` | `{ year: 1, month: 1 }`, unique | Точечный поиск периода при каждой операции над записью — это самый частый запрос в системе. Уникальность запрещает два документа на один месяц |
| `employees` | `_id` (по умолчанию) | Отдельный индекс не нужен: сотрудники запрашиваются по `_id` в `$lookup` и списком целиком |

Запросы по месяцу намеренно формулируются как полуинтервал
`date >= 2026-03-01 && date < 2026-04-01`, а **не** через `$year`/`$month` от
поля: вычисляемое выражение над полем не может использовать индекс и вызывает
COLLSCAN. На «нескольких миллионах записей» это разница между сканированием
месяца и сканированием всей истории.

Это не теория — проверено `explain("executionStats")` на живой базе:

```
полуинтервал:  stage=IXSCAN    index=ix_date_employee_project
$month:        stage=COLLSCAN  index=-
```

Индексы создаются идемпотентно при старте API (`MongoIndexes.EnsureAsync`) и
той же командой перед наполнением базы. Полагаться на то, что индексы кто-то
завёл руками на проде, нельзя: их отсутствие проявляется не ошибкой, а
медленным отчётом под нагрузкой — то есть тогда, когда чинить уже поздно.

### Управление состоянием — TanStack Query (обоснование требует ТЗ)

Всё состояние этого приложения — **серверное**: список записей, справочники,
отчёт. Клиентского состояния, переживающего перезагрузку, здесь нет вовсе, кроме
значений фильтров и открытой модалки — для них хватает `useState`.

Redux и mobx-state-tree решают другую задачу: они хранят состояние на клиенте.
Применённые здесь, они заставили бы вручную писать кэширование, инвалидацию
после мутаций, отслеживание загрузки и ошибок — то есть воспроизводить то, что
TanStack Query даёт из коробки. Ключевой для этого задания сценарий —
инвалидация: после создания, правки или удаления записи и список, и отчёт должны
перечитаться с сервера, потому что стоимость и флаг переработки считает бэкенд,
а клиент их не выводит. В Query это одна строка `invalidateQueries`, в
mobx-store — ручная синхронизация, на которой легко получить ровно тот баг,
который описан в `REVIEW.md` (п. 3–4 по фронтенду): состояние собрано на клиенте
и разошлось с сервером.

Замечание для честности: в боевом проекте заказчика стоит mobx-state-tree, и там
переезд ради одного экрана не оправдан. Выбор сделан для отдельного маленького
проекта, каким и является часть 2.

## 5. Сид-данные

Команда наполнения **идемпотентна и сносящая**: очищает коллекции и заливает
ровно приёмочный набор — 2 сотрудника, 2 проекта, 4 записи табеля.

Это не косметика. Сценарии с ошибками из приёмки создают в базе дополнительные
записи — в частности, 20 часов Иванову на 06.03.2026 (сценарий 2 сохраняется
успешно, как и задумано). Если после их прогона не пересоздать данные, отчёт за
март покажет 32 часа вместо ожидаемых 12 по П-001, и приёмка не сойдётся.
Порядок проверки: `seed` → сверить отчёты → прогнать сценарии ошибок → `seed`
заново.

Записи из раздела «Сценарии с ошибками» в сид **не входят** — это сценарии
ручной проверки, а не эталонные данные.

## 6. Осознанно не сделано

Прямо исключено заданием: аутентификация, роли и права; красивая вёрстка,
адаптивность, тёмная тема, анимации; импорт, экспорт, печатные формы,
уведомления; CI/CD, Kubernetes, микросервисы.

Дополнительно не делаю, считая избыточным для объёма в 4–6 часов:

- **CRUD справочников** сотрудников и проектов через API — ТЗ требует только
  чтение для выпадающих списков; данные заводятся сид-командой;
- **редактирование истории ставок через интерфейс** — сценарий 8 из приёмки
  проверяется правкой в базе либо сид-командой;
- **аудит изменений** — в записи есть служебные поля «кто и когда создал или
  изменил», но отдельного журнала истории нет;
- **локализация** — интерфейс и тексты ошибок только на русском, как требует ТЗ.

2. **Кэш отчёта с инвалидацией через change streams.** Отчёт за закрытый месяц
   не меняется по определению — его незачем пересчитывать при каждом открытии.
   Change streams в стеке заказчика уже используются.
3. **Предагрегация по дням** (`employee + date + project → часы, стоимость`),
   обновляемая при записи. Отчёт за месяц тогда читает тысячи документов вместо
   миллионов, а проверка суточного лимита становится чтением одного документа.
   На объёмах из ТЗ («несколько миллионов записей») это то, что я предложил бы
   на созвоне в ответ на вопрос про масштабирование.
4. **Keyset-пагинация** вместо `skip`/`limit` — при больших `skip` база всё
   равно проходит пропускаемые документы.
5. **`$setWindowFields`** для подсчёта часов по дню одним проходом вместо
   отдельного шага (требует MongoDB 5.0+, поэтому не в базовом решении).
6. **Обработка записей без применимой ставки в отчёте.** Сейчас такие записи
   считаются отдельным счётчиком и видны в ответе. По-хорошему нужен экран
   «проблемные записи», потому что появиться они могут только при правке истории
   ставок задним числом — и это ровно та ситуация, которую бухгалтерия должна
   увидеть, а не обнаружить по расхождению итогов.
